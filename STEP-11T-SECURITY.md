# Step 11T — Durable execution state in the trusted coordinator

## Scope and relation to Steps 11R and 11S

`TrustedToolExecutionService` now requires `IActionExecutionStateStore`. Step 11R's ownership, approval, exact-tool, permission, and policy gates remain independent. Step 11S's immutable state, versioned transition policy, and approval consumption remain in use. No production state-store adapter is registered; the supplied default is unavailable, and only package-free security checks supply a one-state atomic fake. There is no production execution readiness claim.

Step 11R allowed a retained Approved `ActionDescriptor` to invoke a synthetic handler again. With a correctly atomic state store, Step 11T reserves once before any handler invocation; replay of that descriptor returns `StateConflict` without another handler call. The lock-protected fake verifies this behavior and a concurrent two-call race. It does not verify PostgreSQL transactions or provide production replay protection without a real adapter.

## Exact coordinator flow

The internal `ExecutionRequest` still contains only ActionId. It supplies neither an execution ID nor an expected version. The coordinator checks request/scope/action state and exact immutable `ApprovalEvidence`, validates ownership, resolves the exact registered tool and handler, validates permission and independent execution policy, then rechecks ownership. It verifies a UTC start time and derives a Ready version-0 snapshot from the Approved action and evidence. None of these gates is replaced by state storage.

After those checks, the trusted workflow creates one `ExecutionAttemptIdentifier`. `TryReserveInitialAsync` is a single atomic store-boundary operation: a future transactional adapter must create the exact Ready row if absent and reserve it under the same transaction, or compare an existing row against version 0 and reject a reservation/completion. There is no non-atomic Get/Insert/Reserve sequence. The coordinator accepts success only when the returned Reserved state is valid, version 1, and binds the exact action, scope, tool, approval, and attempt ID with `ApprovalConsumedByExecutionId` equal to that ID. A failure or malformed success invokes no handler. The store does not invoke handlers itself. Approval consumption lives in state; `ApprovalEvidence` is unchanged.

Only after successful reservation does the coordinator issue `TrustedExecutionContext` using that **same** attempt ID, create an Executing action, and call the one resolved synthetic handler once. There is no dispatcher, retry, or fallback. Only `ToolExecutionStatus.Success` maps to Succeeded; other, null, or invalid results and non-cancellation handler exceptions map to Failed. Cancellation propagates. Direct `ActionLifecycleService` remains unable to enter Executing/Succeeded/Failed.

After a handler result, the coordinator sends exact action/scope/tool/approval/attempt ID, server-known expected version **1**, and bounded outcome to `TryCompleteAsync`. It returns completed action and `ExecutionEvidence` only when the store returns a valid matching terminal state at version **2**. The same ID appears in the reservation, consumed approval, completion request/state, `ToolExecutionId`, evidence, and structural Step 11Q handoff. Completion failure, exception, null/malformed result, or invalid completion timestamp returns fixed `ReconciliationRequired` with no completed action/evidence; the handler is never retried. A durable Reserved state or external effect may remain.

## Fixed results and resource bounds

Reservation `InvalidRequest` maps to execution `InvalidRequest`; `ScopeMismatch` to `ScopeDenied`; `ApprovalMismatch` to `ApprovalDenied`; `ToolMismatch` to `UnknownTool`; `StaleVersion`, `AlreadyReserved`, `AlreadyCompleted`, and `ExecutionMismatch` to `StateConflict`; `NotFound`, `InvalidState`, `Unavailable`, `Failed`, and unexpected statuses to `StateUnavailable`. An exception or null result from an attempted reservation may follow a committed write and therefore maps to fixed `ReconciliationRequired`; exceptions before the store call map to fixed `Failed`. All completion failures after reservation map to fixed `ReconciliationRequired`. No store message, raw exception, stack, path, handler output, or secret enters the result. Messages are at most 80 characters.

The request has one action ID and no arguments, free text, metadata, or collection. State has fixed identifiers, three scope GUIDs, a tool ID with the existing 64-character limit, a `long` version, bounded status/outcome, and optional fixed IDs. The fake has one fixed state slot and a lock; it is never registered in production. The versioned Step 11S policy still rejects negative/stale versions, malformed state, and overflow. A future adapter must enforce atomic compare-and-swap and approval uniqueness across rows.

## Cancellation, reconciliation, and verification

Cancellation before reservation prevents the handler. Cancellation during reservation may be observed after the store commits: the coordinator checks the token immediately afterward and invokes no handler, leaving a reservation for reconciliation. Cancellation after reservation but before handler likewise invokes no handler. Cancellation during or after the handler propagates and may leave an external side effect with only a Reserved state. Cancellation during completion propagates; completion may or may not have committed and must be reconciled. No handler retry occurs in any case. A future transactional adapter and reconciliation/outbox design are required; database commit and external tool/OS effects cannot be made atomic by this coordinator. There is no distributed or external side-effect exactly-once guarantee.

Execution success does not mean verification. `IsVerified` remains false, `VerificationId` remains null, and `VerificationWorkflowService` is never called. Evidence offers only a structural Step 11Q handoff; a future trusted source must independently attest provenance. No `AIAction`, `ActionApproval`, `ToolExecution`, `Verification`, `Permission`, or `AuditLog` entity is automatically persisted.

## Verification and deferred runtime

Package-free security checks cover gates, state-status mappings, reserve-before-handler, shared execution ID, replay denial, concurrent atomic fake calls, handler outcomes/exceptions, completion failure, cancellation, fixed messages, and the unchanged public request. The full suite includes all previous checks. The fake demonstrates exactly one reservation and at most one handler call for two concurrent coordinator calls; it does not demonstrate database isolation.

No DbContext, EF configuration, schema, migration, package, PostgreSQL adapter, production in-memory store, real handler, shell/Git/filesystem/browser/HTTP/MCP execution, provider tool calling, automatic verification, or chat integration was added. Safe File Access remains disabled, and AiChatRequest remains Prompt-only. No real PostgreSQL, OpenAI, or Ollama call was made. PostgreSQL/pgvector behavior, production ownership/permission/policy adapters, cross-row approval uniqueness, real handler side effects, reconciliation, semantic retrieval/ranking, and live OpenAI/Ollama remain runtime-unverified and deferred.
