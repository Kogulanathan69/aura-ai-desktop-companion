# Step 12D — Endpoint identity mapping alignment

The older `UserIdentityService` queried `Users` directly with `FirstOrDefaultAsync` on `AuthUserId`. That could resolve an inactive account and conceal duplicate active rows. It now depends on the Step 12C `IAuthenticatedUserMappingSource`, so existing endpoint services receive an internal `User.Id` only from one exact, active, nonempty `Found` mapping whose `AuthUserId` echoes the authenticated subject. Missing, inactive, duplicate, unavailable, malformed, empty, mismatched, and unknown results deny with a bounded `UnauthorizedAccessException`. Mapping dependency errors do not leak or trigger a retry/fallback; cancellation propagates. The public `IUserIdentityService` remains `Task<Guid>`, with no entity, status, claim, email, or role returned.

`CurrentUserService` still uses only canonical `sub` from ASP.NET's authenticated principal. Its subject extraction now requires one authenticated identity and one `sub` belonging to that identity, so duplicate or cross-identity claims cannot be silently selected by `FindFirst`. It does not parse JWTs, use a new claim, or fall back to `NameIdentifier`, email, role, header, route, query, or body. The API's authority, audience, and token validation settings are unchanged.

`Aura.Api/Program.cs` keeps the existing scoped `IUserIdentityService` registration and adds only scoped `IAuthenticatedUserMappingSource` → the reviewed read-only `AuthenticatedUserMappingSource`. This source serves existing endpoint identity lookup; it does not register `HttpCurrentUserContext`, `OwnershipPersistenceSource`, or `ExactOwnershipScopeValidator` for production workflows. Startup still uses `UnavailableRuntimeCapabilityReadiness` with ownership false, and runtime safety defaults remain disabled.

Existing endpoints that previously accepted inactive users or an ambiguous active mapping now deny before accessing their resources. Duplicate or cross-identity `sub` claims also deny. Valid, exact active mappings still return the same internal user ID. No user is created or updated, and there is no `SaveChanges`, permission grant, approval, execution, or audit write.

Package-free checks exercise the actual read-only mapping source through the existing query test seam and the service through a bounded fake and authenticated endpoint principal: exact active mapping, inactive/missing/duplicate rows, empty or malformed subject, dependency failure, exact echo, unknown statuses, cancellation, one lookup without retry, and canonical-claim ambiguity. The prior security suite remains intact. With .NET 10.0.401, the solution build passed with no warnings or errors and the full suite passed 1,163 checks.

No schema, migration, DbSet, EF configuration, package, token issuance, new claim, production ownership workflow, Safe File Access enablement, real tool handler, or live OpenAI/Ollama call was added. JWT and PostgreSQL runtime behavior, EF translation, and production ownership authorization remain unverified. This step does not make production authorization ready.
