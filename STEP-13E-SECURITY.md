# Step 13E — typed security persistence foundation

This step adds three dedicated tables. Legacy `AuditLogs`, `Verifications`, `ToolExecutions`, and `AIActions` are not reinterpreted or changed. The tables carry no text/JSON provenance substitutes, seed rows, wildcard or admin bypass fields.

## Audit

`SecurityAuditEvents` has a unique nonempty `Id`, constrained numeric `EventType` (the existing 12-value application enum) and `Outcome` (four values), required UTC `OccurredAt`, required nonempty `UserId`, `ConversationId`, `ProjectId`, and optional typed `ActionId`, canonical `ToolId` (maximum 64), `ApprovalId`, `ExecutionId`, `VerificationId`, `ReconciliationId`, and `PermissionGrantId`. Optional UUIDs reject empty values. Required scope foreign keys use Restrict. Optional references are typed identifiers but are not foreign keys; the current in-memory workflow may emit observations before corresponding rows are persisted. The application event validator retains event-family rules.

The unregistered `SecurityAuditPersistenceSink` maps one bounded `AuditEventRecord` to one insert using a fresh EF context. It returns Accepted only after one row is saved, rejects a duplicate event ID with bounded Failed, maps other database errors to Unavailable, propagates cancellation, and does not retry. This is a **direct sink**, not an outbox. Execution-state updates and audit inserts do not share a transaction. Observational audit calls can fail after business state changes, so exactly-once audit delivery, reliable ordering, append-only enforcement, and tamper evidence are not established. Audit readiness stays false.

## Reconciliation

`ExecutionReconciliationAssessments` has a unique nonempty assessment `Id`, exact required action/user/conversation/project/tool/approval/execution bindings, Reserved status and version 1 observation, bounded reason (six values) and advisory disposition (NeedsManualReview or SafeToMarkFailed), and required `AssessedAt`. Required foreign keys to `ActionExecutionStates`, `Users`, `Conversations`, `Projects`, and `ActionApprovals` use Restrict. Only the assessment ID is unique; repeated assessments of the same execution/version are possible and no idempotent assessment writer is claimed. No assessment write adapter is introduced.

The unregistered read-only `ExecutionReconciliationPersistenceSource` reads `ActionExecutionStates` under an EF RepeatableRead transaction with an exact action and scope predicate. It checks canonical tool ID, state shape/version/timestamps, and the active user, owned project, project conversation, action, and approval chain. It returns a bounded snapshot with `Reason.Unknown`, since storage cannot infer why reconciliation was requested. Malformed, absent, foreign, or database-error states return null. Cancellation propagates. It uses `AsNoTracking`, never reads generic `ToolExecution.Status`, retries a handler, or mutates execution state. The advisory service still does not persist its generated assessment evidence. Reconciliation readiness stays false.

## Verification

`ExecutionVerificationAssessments` has a unique nonempty verification `Id`, exact required action/user/conversation/project/tool/approval/execution bindings, terminal execution status, bounded verification outcome, proof source/version, and required `AssessedAt`. Required foreign keys to `ActionExecutionStates`, `Users`, `Conversations`, `Projects`, and `ActionApprovals` use Restrict. There is no unique `ExecutionId` rule: multiple assessments could be retained, subject to a future reviewed writer policy. With no independent proof provider, the database currently permits only Failed or Inconclusive and requires `ProofSource=None`, `ProofVersion=0`; it rejects a durable Verified claim. No verification writer, trusted `IExecutionEvidenceSource`, or independent proof policy is added. Neither a successful execution report nor AI text becomes proof. Verification readiness stays false.

## Migration, runtime, and remaining work

Manual migration `20261014000002_AddSecurityPersistenceBundle` creates only these tables and their indexes; rollback drops only these tables. It copies no data and is never automatically applied. The historical EF migration baseline/snapshot remains unresolved, so this chain is not cleared for production. The individual foreign keys do not establish composite equality among every scope and provenance field; this remains a production integrity concern. No live PostgreSQL schema or adapter test was run in this step. The controlled Step 13D concurrency run is also still pending.

The API registers none of these adapters. Startup and informational AuditSink, Reconciliation, Verification, and ExecutionState readiness remain false. `ProductionAdaptersEnabled`, `ToolExecutionEnabled`, and Safe File Access remain disabled. No real tool execution, OpenAI/Ollama call, or production migration application occurs. Step 13F should review the migration baseline and composite binding integrity, run disposable PostgreSQL verification, define a transactional audit/outbox strategy, add assessed-reconciliation persistence with explicit idempotency, and design real independent verification proof before any readiness can be enabled.
