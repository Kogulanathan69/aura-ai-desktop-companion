# Step 11Z — Runtime safety configuration and startup validation

Step 11Z adds a startup-only coordination gate for existing runtime settings and future production capabilities. It adds no production adapter, live probe, handler, or persistence implementation.

`RuntimeSafetyOptions` binds from `Security:RuntimeSafety`. Its five booleans—`ProductionAdaptersEnabled`, `ToolExecutionEnabled`, `SafeFileAccessEnabled`, `CloudAiEnabled`, and `AuditPersistenceEnabled`—all default to `false`. The section is omitted from `appsettings*.json`, so the safe defaults apply. It contains no secret, endpoint, role, token, or connection property.

`IRuntimeCapabilityReadiness` returns a bounded snapshot for ownership, permission, execution state, audit sink, reconciliation, verification, handler, execution policy, and Safe File Access. The only registered implementation, `UnavailableRuntimeCapabilityReadiness`, reports all false. This is an explicit assertion boundary for future reviewed registrations, not a DI-container inspection or a claim that an adapter exists.

The pure `RuntimeSafetyValidator` accepts snapshots and returns a bounded status. Missing inputs or an unknown router mode are invalid. The safety file flag must agree with `ProjectFileAccessOptions.Enabled`; even when both are true, file readiness is required. The cloud flag must agree with both Cloud router mode and `OpenAiOptions.Enabled`. This preserves Local routing by default. Tool execution and audit persistence require production-adapter mode. Production mode requires ownership, permission, execution-state, audit-sink, reconciliation, and verification readiness. Tool execution additionally requires real handler and execution-policy readiness. Audit persistence requires audit-sink readiness. Because every production readiness flag is currently false, attempted enablement of those capabilities fails closed. A deliberate, consistent cloud configuration can pass this coordination gate; the existing OpenAI configuration validator still applies, and no live cloud behavior is verified here.

`Aura.Api/Program.cs` binds the options once, evaluates the gate before building the host, and registers only the options, validator, and unavailable readiness implementation. Unsafe combinations throw the fixed message `Runtime safety configuration is invalid.` Runtime safety binding errors use the same message. Validation performs no DB, HTTP, provider, or tool call and has no retry or fallback. The existing connection and JWT startup requirements still apply; safe-disabled refers to the new runtime capabilities, not a claim that the application starts without its prior configuration.

Safe File Access remains disabled by default and is never enabled by the new flag alone. Production adapters, execution, and durable audit persistence remain disabled by default. No production adapter, real tool handler, DbContext/EF/schema/migration/package change, chat/provider behavior change, API key, or connection string was added. PostgreSQL/pgvector integration, production ownership and other adapter validation, semantic retrieval/ranking, live OpenAI/Ollama runtime, and real tool execution remain deferred or unverified. This is not production readiness.

Package-free Step 11Z checks cover defaults, binding, readiness, unsafe combinations, cloud coordination, invalid modes, and the safe failure message. The full suite retains all prior security checks. With .NET 10.0.401, solution restore and `dotnet build Aura.slnx --no-restore` passed; the full security suite passed 1,079 checks.
