# Step 13C: durable execution-state foundation

This step adds `ActionExecutionStates` independently of historical `ToolExecutions`. It does not enable a production execution path. `ActionId` is the primary key, so one action has at most one state row. Required exact bindings are `ActionId`, `UserId`, `ConversationId`, `ProjectId`, canonical `ToolId` (at most 64 characters), and `ApprovalId`. `ExecutionId` is null only before reservation. The row also stores typed status, bigint CAS version, explicit `ApprovalConsumed`, and created/reserved/completed UTC timestamps. No row is seeded or copied from an existing execution table.

The database check constraints admit only Ready/version 0/unconsumed/no execution or later timestamps; Reserved/version 1/consumed/execution and reservation timestamp/no completion timestamp; and Succeeded or Failed/version 2/consumed/execution and both later timestamps. All required UUIDs and nonnull execution UUIDs reject `Guid.Empty`. The approval index is unique and the execution index is unique for nonnull IDs. The primary key uniquely binds the action. Required single-column foreign keys to `AIActions`, `Users`, `Conversations`, `Projects`, and `ActionApprovals` all use Restrict. These FKs ensure the referenced rows exist; they do not independently prove that the referenced action, approval, user, conversation, and project belong together. The trusted workflow and exact store predicates must maintain that relationship, and a future live review should assess composite binding constraints.

`ActionExecutionStatePersistenceStore` implements the existing application contract but is not registered in `Aura.Api`. Each operation uses a fresh context from `IDbContextFactory<AuraDbContext>` so an insert cannot flush unrelated tracked changes. Initial reservation starts an EF transaction, reads the action state, inserts Ready/version 0 if absent, and performs a conditional `ExecuteUpdateAsync` to Reserved/version 1. The insert's action primary key and approval unique index resolve concurrent insert/replay races; execution ID uniqueness resolves cross-row execution reuse. A loser receives a bounded conflict result. Existing Ready rows undergo exact binding and policy checks before conditional update. Reservation's predicate includes action, user, conversation, project, tool, approval, Ready, expected version, and unconsumed/null execution and timestamps. Completion's predicate adds the exact execution ID, Reserved, version 1, consumed flag, and timestamp shape, then changes to Succeeded or Failed/version 2. One affected row is required. Stale or duplicate operations fail closed. There is no handler call, retry, raw SQL, or external side effect in the store. Cancellation propagates; database failures map to bounded `Unavailable`, with recognized uniqueness violations mapped to a bounded conflict. Returned state is constructed from the policy result after a successful conditional update and transaction commit.

The targeted manual migration creates only the new table and indexes; rollback drops that table. It is not automatically applied. Historical EF baseline and model snapshot are still absent, so the full migration chain needs human review before production application. Offline checks inspect the compiled EF model and migration operations, store guard structure, and disabled runtime configuration. They do not prove PostgreSQL transaction behavior or live concurrency. No live database write or concurrent test was run. A controlled disposable PostgreSQL concurrency harness and real schema/FK verification remain Step 13D work.

Startup `ExecutionState` readiness and informational readiness remain false. `ToolExecutionEnabled`, `ProductionAdaptersEnabled`, and Safe File Access remain disabled. No production store or context-factory registration, tool handler execution, or OpenAI/Ollama call is introduced. Later integration must register a reviewed context factory and ensure trusted action and approval rows exist before reservation. This foundation does not establish production exactly-once execution.
