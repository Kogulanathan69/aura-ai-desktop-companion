# Step 12E — Ownership runtime wiring readiness

Step 12E defines an explicit, future-only DI composition method. It does not enable production ownership authorization. Normal `Aura.Api/Program.cs` does not call `AddOwnershipRuntimeFoundation` and still uses `UnavailableRuntimeCapabilityReadiness`, with ownership false. No new runtime config option was added.

The isolated ownership chain is authenticated request → one canonical `sub` → reviewed `AuthenticatedUserMappingSource` → internal `User.Id` → `HttpCurrentUserContext` → `ExactOwnershipScopeValidator` → read-only `OwnershipPersistenceSource` → active user, owned Project conversation, exact conversation/project relation, and owned project. The current-user and ownership-data checks are both required; neither an external subject nor an internal ID supplied in a scope can bypass them.

`AddOwnershipRuntimeFoundation` is a named, explicitly invoked API registration method. It requires exactly one scoped `IAuraDbContext`, reuses the existing scoped `AuthenticatedUserMappingSource` or registers that exact reviewed type if absent, and rejects conflicting mapping or ownership registrations. It registers `ICurrentUserContext`, `IOwnershipSource`, and `ExactOwnershipScopeValidator` as scoped. All five workflow ownership interfaces—action, approval, tool execution, verification, and reconciliation—resolve the same scoped validator instance. A new request scope gets a different instance. The framework `IHttpContextAccessor` remains request-safe; no request identity is cached as a singleton. Calling the method performs no database, JWT, HTTP, provider, or tool probe.

The method is deliberately absent from normal startup. `Program.cs` continues to register the mapping source only for existing endpoint identity resolution; it does not register `HttpCurrentUserContext`, `OwnershipPersistenceSource`, `ExactOwnershipScopeValidator`, or any workflow ownership interface. The informational `PersistenceCapabilityReadiness` reports implementation presence, not production readiness, and is not the startup readiness source. Even `ProductionAdaptersEnabled=true` cannot make ownership ready while startup uses all-unavailable readiness. Future enablement requires separate live JWT verification, live PostgreSQL mapping and ownership-query verification, explicit reviewed registration, and the other production adapter requirements.

Ownership alone never grants permission, approval, execution policy, durable reservation, verification, or audit persistence. Tool execution and Safe File Access remain disabled. No live probe, retry, fallback, production handler, schema, migration, DbSet, EF configuration, package, or live OpenAI/Ollama call was added.

Package-free Step 12E checks invoke the helper only in an isolated service collection with the existing query-only database seam. They verify scoped lifetimes, reuse of the reviewed mapper, the same validator instance across five interfaces, exact identity/ownership decisions, foreign and inactive denials, and conflict rejection without partial registration. Prior checks remain intact. With .NET 10.0.401, the solution build passed with no warnings or errors and the full security suite passed 1,181 checks. Live production ownership remains unverified and disabled.
