# Step 13K — disposable PostgreSQL outbox hardening verification

This adds an explicit `security-checks` command for the Step 13J check constraint and reuses the Step 13I real dispatcher scenarios. It does not register the dispatcher in `Aura.Api`, enable runtime readiness, execute tools, access project files, or call AI providers. The normal security suite remains offline.

The command is `dotnet run --project security-checks/Aura.SecurityChecks.csproj -- --live-audit-outbox-hardening`. It requires **both** `AURA_LIVE_AUDIT_OUTBOX_VERIFY=true` and `AURA_AUDIT_OUTBOX_DB_IS_DISPOSABLE=true`. Without either flag it prints `LIVE AUDIT OUTBOX VERIFY: SKIPPED`, exits successfully, and does not read connection configuration. It reads `ConnectionStrings__DefaultConnection` only after both flags are present. The explicit connection must name an existing database beginning `aura_disposable_` and supply a host and username. This naming rule is a guardrail; the operator must independently confirm that the target is disposable. No credential is stored in the repository.

Before any migration, the command checks connectivity, the outbox and audit-event tables, exact ordered migration history through Step 13G, and the current delivery constraint expression. It counts `Failed` rows with nonnull `DeliveredAt`. A nonzero count prints `PRE-MIGRATION DATA CHECK: FAIL`; no migration or repair occurs. Other malformed baseline states also fail closed.

Migration application additionally requires `AURA_ALLOW_AUDIT_OUTBOX_MIGRATION=true`. The command verifies that Step 13J is the **only** pending migration, then targets `20261014000004_HardenSecurityAuditOutboxDelivery` with EF's migration API. It never calls `EnsureCreated`, resets a database, applies later migrations, or repairs data. If Step 13J is already applied and the exact new constraint is present, migration application is skipped. The historical core schema baseline is still unresolved in this repository; a separately reviewed disposable baseline with the exact prior migration history is required. The command cannot bootstrap an empty database.

After application or an already-hardened baseline, the command checks that the Step 13J history ID is recorded and that PostgreSQL reports the exact new constraint expression: Pending has zero attempts and null `DeliveredAt`; Delivered has positive attempts and nonnull `DeliveredAt`; Failed has positive attempts and null `DeliveredAt`. It uses generated fixture IDs to require database rejection of a Failed row with a nonnull timestamp and acceptance of all three valid shapes. It then reuses the Step 13I dispatcher tests for accepted and failed delivery, unavailable sink, duplicate event IDs, concurrency, terminal redispatch, cancellation, malformed event, and exact binding. Fixture cleanup runs in `finally`, deletes generated IDs in dependency order, and verifies absence. Output uses only fixed PASS/FAIL/SKIPPED categories and does not print database details.

**No live PostgreSQL command was run on this PC.** No migration was applied, and invalid-row rejection, valid shapes, dispatcher delivery, and cleanup remain unverified against PostgreSQL. Static checks and build results are not live evidence. A real disposable run may expose migration baseline, catalog formatting, transaction, or cleanup issues that require review. Exactly-once delivery is not claimed; external side effects may duplicate after a crash or cancellation. Production AuditSink and ExecutionState readiness remain false. Production adapters, Tool Execution, Safe File Access, and Cloud AI remain disabled. Final readiness work includes a reviewed migration baseline, a passing disposable run, production delivery/recovery policy, and separate security approval before registration.
