# Step 16H — genuine production allowing-policy checkpoint

**Decision: blocked; ExecutionPolicy=false.** `IToolExecutionPolicy` currently receives only a registered `ToolDescriptor` and cancellation token. Its only concrete production implementation is `DenyToolExecutionPolicy`; the reviewed policy catalog is empty and normal API startup registers no policy. No exact production tool or handler has been selected, so an allow rule cannot name a meaningful, reviewed ToolId/capability/required-permission tuple. An `AllowAll`, synthetic allow fixture or arbitrary tool ID would violate Step 15H's evidence boundary. No allowing implementation, DI registration or catalog entry is added.

Design decision remains open: keep a descriptor-only policy strictly as an independent *feature enablement* check after separately proven ownership, approval and permission gates, or introduce a small immutable action/scope context if policy must bind ActionId, UserId, ConversationId and ProjectId itself. Do not assume the existing descriptor carries those identities. A future policy must default deny, allow only explicit canonical reviewed IDs with exact capability/permission pairings, reject unknown or malformed metadata, propagate cancellation, and have no network, retry, fallback or arbitrary payload. Approval, ownership, permission and handler presence remain separate necessary gates; none authorizes by itself.

The existing deny policy and trusted call site retain fail-closed behavior. No live DB evidence applies to this pure deny-only checkpoint. Production flags, all ten composition fields and activation remain false.
