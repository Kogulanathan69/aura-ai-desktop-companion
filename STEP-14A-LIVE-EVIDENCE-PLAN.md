## Gates and database selection verified from source

**A — ownership.** `LiveOwnershipVerification` checks only `AURA_LIVE_OWNERSHIP_VERIFY` before reading inputs; absent or any value other than `true` exits `SKIPPED` with no connection. It requires a nonblank `ConnectionStrings__DefaultConnection` and four nonempty GUIDs. It does **not** parse the connection string, enforce a disposable database name, or require a disposable acknowledgement. The operator must independently verify the host/database, use a read-only PostgreSQL account, and select an existing active user, Project conversation and owned project. This harness uses a fixed current-user test seam, **not** a real Supabase JWT or HTTP request.

**B — permission.** `LivePermissionVerification` checks `AURA_LIVE_PERMISSION_VERIFY` first. It requires an explicit host and database in `ConnectionStrings__DefaultConnection`, four nonempty GUIDs (including the optional grant ID if supplied), a canonical tool ID, and one exact requirement value: `OwnedProjectRead`, `OwnedProjectWrite`, or `ExternalAction`. It has **no disposable acknowledgement** or database-name restriction. Use a manually verified controlled test database and read-only account. A known existing, active, non-revoked exact grant must be selected before the run; `NO TEST GRANT` is a failure, not PASS. The harness does not issue or revoke grants.

**C — execution state.** Both `AURA_LIVE_EXECUTION_STATE_VERIFY` and `AURA_EXECUTION_STATE_DB_IS_DISPOSABLE` must equal `true` before the connection is read. The Npgsql connection string must contain a host and database. The code does **not** enforce a disposable name or read-only account; because it writes, an operator must verify the actual database identity and use a dedicated disposable test database. No migration is applied. Its catalog gate requires `20261014000001_AddActionExecutionStates`, exact state columns/checks/Restrict foreign keys, and unique approval and execution indexes before fixtures are created.

**D — hardening.** Both `AURA_LIVE_AUDIT_OUTBOX_VERIFY` and `AURA_AUDIT_OUTBOX_DB_IS_DISPOSABLE` must equal `true` before connection settings are read. `ConnectionStrings__DefaultConnection` must provide host, username, and an existing database name beginning `aura_disposable_`; that prefix is a guardrail, not proof of disposal. The command requires the outbox and audit tables, `__EFMigrationsHistory`, exact ordered migration IDs 00000–00003 (or 00000–00004 if already hardened), and the corresponding old/new delivery constraint. It counts `Failed` rows with nonnull `DeliveredAt`; any such row blocks migration and is **not repaired**. When 00004 is pending, `AURA_ALLOW_AUDIT_OUTBOX_MIGRATION=true` and an exact single pending migration are required before EF targets `20261014000004_HardenSecurityAuditOutboxDelivery`. If 00004 is already applied with the exact new constraint, the migration step reports `SKIPPED` and can continue without the migration gate. This is the **only** command in this plan that can apply a migration. It cannot bootstrap an empty database or resolve the historical core-schema baseline.

**D2 — standalone dispatcher.** The same live and disposable flags are required, but its connection comes from **`AURA_AUDIT_OUTBOX_DISPOSABLE_CONNECTION`**, not `ConnectionStrings__DefaultConnection`. It requires host, username and `aura_disposable_` database name, existing core tables, and applied migration IDs through 00004. It writes fixtures and never calls `MigrateAsync`. D already invokes its real dispatcher scenarios, so D2 is an optional independent repeat, not a substitute for D's migration and schema checks.

Before **every** run, independently verify the exact target host/database and its owner, that it is a controlled test environment, backups/disposal policy, access rights, the selected repository commit, relevant migration history and schema, and that the environment variables belong to this shell session. Never infer safety from a string prefix or a `*_IS_DISPOSABLE=true` flag. Stop on any unexpected migration history, schema, target, missing fixture, or failed cleanup; do not invent history entries or weaken checks. The historical core-schema baseline and model snapshot need a separate reviewed preparation procedure before C or D can produce meaningful PASS evidence.

## What remains after the sequence

If **A** is skipped, live database mapping/ownership evidence is absent. If **B** is skipped, exact grant lookup/schema evidence is absent. If **C** is skipped, single-winner reservation, approval consumption, conflict and completion behavior remain unverified on PostgreSQL. If **D** is skipped, the Step 13J migration/constraint, invalid-row rejection and audit dispatcher behavior remain unverified; D2 alone cannot close the migration gap. If **D2** is skipped after a complete D PASS, no additional Step 13I repeat is lost. A skipped final review means the evidence has not been judged together and no activation decision may change.

Even after A–D PASS, Step 13L remains **NOT READY** until separate reviewed live Supabase JWT/subject behavior; a historical migration baseline; grant issuance/revocation policy; independent verification and durable reconciliation evidence; production audit delivery/recovery/idempotency design; reviewed allowing execution policy and real handlers; explicit DI/lifetime composition and flags; Safe File Access or Cloud AI reviews if enabled; and final security approval exist. Successful offline or live harnesses do not enable production runtime or prove exactly-once execution or audit delivery.
