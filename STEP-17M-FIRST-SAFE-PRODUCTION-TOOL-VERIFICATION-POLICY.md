# Step 17M — first safe production tool, verification and policy design

## Decision and selected candidate

**Design candidate: an owned-project metadata read, proposed canonical ID `owned-project-metadata-read`, `ProjectRead` capability and `OwnedProjectRead` required permission. No production tool is selected for registration yet.** It has a real potential use: return a bounded, non-sensitive status/name summary for the approved project, without file contents, external providers or mutation. It would be deterministic for one observed project version and would need no shell, process, arbitrary URL or unrestricted path. Its proposed descriptor must remain disabled until the complete target, proof and execution chain has been reviewed. A fixed-success/no-op handler is not a substitute.

The Safe File Access subsystem is **not** this tool. `SafeProjectFileContentService` returns `Unavailable` when `ProjectFileAccessOptions.Enabled` is false, and `SafeFileAccessEnabled` remains false. A file-reading handler would bypass separate path, privacy and runtime gates. No alternate local utility with a bounded, approval-bound target and independently observable result is available in the present tool contracts.

**Outcome:** no `IToolHandler`, independent `IExecutionEvidenceSource`, verification assessment writer, or allowing `IToolExecutionPolicy` was implemented or registered. `ToolHandlers=false`, `Verification=false` and `ExecutionPolicy=false`. This is the conservative design-review branch explicitly allowed when a safe real tool cannot yet be selected. The source remains deny-only; no runtime execution was enabled.

## Threat model and trusted target binding

The current `ToolInvocationRequest` is immutable but contains only `ToolId`. `TrustedToolExecutionService` constructs it as `new ToolInvocationRequest(action.ToolId)` after scope, approval, permission, policy and reservation checks. The **approved target is not carried** to the handler. A handler receiving only the tool ID cannot know which project it is authorized to read. Reconstructing a target from arbitrary request data, ambient environment, the most recent project, or an unscoped query would introduce a confused-deputy path. No caller-supplied `UserId`, target path, URL, command, dictionary, JSON, permission or capability may become authority.

The minimal proposed immutable value object is a sealed server-created `OwnedProjectMetadataTarget` containing the action ID, internal user ID, conversation ID, project ID, canonical tool ID and approval ID, plus the specific approved project ID constrained to equal the action scope's project ID. It must be built from the approved `ActionDescriptor` and matching `ApprovalEvidence`, after authenticated ownership resolution, and frozen before reservation. The same target identity must travel into the one handler call and subsequent independent verification; the execution ID/version should be attached after reservation, never supplied by a client. Constructor validation must reject empty IDs, inconsistent scope/project, noncanonical tool metadata and unapproved resource kinds. No arbitrary text or secret field belongs in the target.

For **project ID alone**, the existing `ActionDescriptor.Scope.ProjectId` and approval-to-action binding may provide an approval-bound resource, provided the future code proves the approval snapshot cannot be switched and validates the exact scope immediately before execution. This has not been implemented or tested. If the intended operation needs an approved metadata field selection, expected value, revision or digest, the present action/approval records have no such immutable target specification. That would require a separately reviewed model/schema change and migration source; silently adding such a field after approval would not authorize it. The current database's historical core-schema provenance is also partially unresolved by Step 17K.

## Handler and registry design

An eventual `OwnedProjectMetadataReadHandler` would be sealed and scoped, accept only the trusted typed target, recheck active local user and exact owned project/conversation binding, read a fixed allowlist of metadata fields with `AsNoTracking`, propagate cancellation, return only a bounded observation, and map storage errors to fixed statuses. It must not expose `LocalPath`, repository credentials, file content or raw database exceptions. It has **no intended mutation**, no retry and no external side effect; repeat reads would be idempotent except for legitimate changes to project metadata between reads. Audit observation must reference the exact action/scope/tool/approval/execution IDs without logging the metadata body.

An explicit one-entry `ToolRegistry` would pair `owned-project-metadata-read` with that exact descriptor and handler. Registry duplicate IDs and unknown IDs must continue to be denied. Normal startup does not currently register `ToolRegistry`, `IToolHandler` or a dispatcher; source presence alone cannot establish the descriptor/handler pairing. No handler DI descriptor or reviewed `ReviewedToolHandlers` catalog tuple is added in Step 17M.

## Independent verification and assessment persistence

A handler's `Success` status or returned metadata is **not** independent verification proof. For this candidate, the verifier would need to re-observe the same authoritative owned project *independently* and compare a bounded handler observation tied to the exact approved target and execution. Merely seeing that the project currently exists does not prove the handler observed it. If metadata changes between reads, the policy needs a reviewed version/freshness rule; it must return `Inconclusive` or `Failed` as appropriate, never a fabricated `Verified`. A read-only operation also has no lasting postcondition that proves an invocation occurred, so even a matching independent read needs a clear claim: it could verify the result's consistency with authoritative state, not prove historical handler execution by itself.

The proposed proof designation would be `OwnedProjectMetadata` with version `1`, but **neither exists as a production proof source/version today**. `ExecutionEvidenceInput` contains action, user/conversation/project scope, tool, approval, execution, outcome and completion time, but lacks durable execution version and independently attested proof metadata. An eventual adapter must supply bounded proof source/version, observation or digest, UTC observation time, and exact action/user/conversation/project/tool/approval/execution/version bindings from independent state. Wrong or stale bindings, unknown source/version, missing proof and a mere success report must never become `Verified`. Current `ConservativeVerificationPolicy` returns `Inconclusive` for a success report.

`ExecutionVerificationAssessments` is schema-only: there is no production assessment writer. Its check constraint permits only Failed/Inconclusive outcomes, `ProofSource=None` and `ProofVersion=0`; **Verified is forbidden by the current database check**. The row also lacks a durable execution-version field. A real Verified assessment therefore needs a reviewed proof model and migration source before a writer can persist it. Step 17M creates no migration, does not apply one, and does not claim the current schema supports Verified. A future scoped writer would insert one exact bounded advisory row, never mutate execution state, propagate cancellation, use no automatic retry, and explicitly allow separate repeated assessment IDs only if that remains the reviewed policy. A persisted assessment alone would not imply Verified.

## Exact allowing-policy design

`IToolExecutionPolicy` currently receives only `ToolDescriptor`; it has no action, scope, approval or target. The only production implementation is `DenyToolExecutionPolicy`. **No allowing production policy was implemented.** An eventual policy context should be a sealed immutable server-created value containing the exact registered descriptor, action ID, internal user/conversation/project IDs, approval ID, reserved execution ID and the approved target kind/identity. The trusted service should build it after independent ownership, permission and approval gates. It must not accept arbitrary payloads or caller-defined capability/permission flags.

The future policy would default deny and allow only the single canonical ID `owned-project-metadata-read` with exact `ProjectRead`/`OwnedProjectRead` metadata, an approved owned-project target matching action scope, valid nonempty IDs and a reviewed active feature gate. It must deny malformed/unknown descriptors, target or enum values; ownership, permission, approval or handler presence alone cannot allow. It must propagate cancellation and have no network, retry, fallback or `AllowAll` branch. No `ReviewedExecutionPolicy` catalog entry or scoped normal-startup registration is added until the target and handler contract exist.

## Readiness, live evidence and rollback

No live tool command was added or run: there is no safely invocable production handler or independent proof adapter. The existing gated `--live-production-verification-evidence` harness truthfully reports `INCOMPLETE` for absent independent proof; running it cannot establish this proposed tool. A future live command must be separately gated to an independently verified disposable/local target, run only the exact reviewed tool with generated or approved harmless fixtures, re-read authoritative state, and report bounded results with cleanup. No production user data may be used.

All ten composition fields remain false: Ownership, Permission, ExecutionState, AuditSink, AuditDelivery, Reconciliation, Verification, ExecutionPolicy, ToolHandlers and TrustedExecution. `CompositionComplete=false`. `ProductionAdaptersEnabled=false`, `ToolExecutionEnabled=false`, `AuditPersistenceEnabled=false`, `SafeFileAccessEnabled=false`, `CloudAiEnabled=false`. `UnavailableRuntimeCapabilityReadiness` and the unavailable final approval source still deny activation. TrustedExecution is not registered. The Step 14 exact catalog and composition rules are unchanged.

Remaining work before implementation: agree on an approval-bound target and metadata observation contract; decide whether a read-only observation can meet the intended independent proof claim; review action/approval persistence implications; design proof source/version and execution-version freshness; prepare and separately review any necessary migration source without auto-applying it; implement and test the real handler, independent adapter, assessment writer and exact policy; review explicit registry and scoped DI/catalog pairings; and obtain genuine live evidence. If this checkpoint is rolled back, remove only this review, `FirstSafeProductionToolChecks.cs` and its one call in `security-checks/Program.cs`; no production behavior or schema changed.
