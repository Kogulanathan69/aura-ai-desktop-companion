# Step 12I — Audit persistence and transactional outbox readiness

Step 12I reviewed `AuditLog` and the EF model against the bounded Step 11W audit contract and Step 11X observational workflow calls. The current table cannot represent those events exactly, and no shared business-state/audit transaction or outbox exists. No production `IAuditEventSink` adapter was implemented or registered. The default sink remains unavailable; audit persistence readiness remains false.

## Contract and schema compatibility

`AuditEventRecord` contains a unique event ID, typed event type and outcome, exact nonempty `UserId`/`ConversationId`/`ProjectId` scope, server UTC occurrence time, and optional typed `ActionId`, `ToolId`, `ApprovalId`, `ExecutionId`, `VerificationId`, `ReconciliationId`, and `PermissionGrantId`. `AuditEventValidation` constrains which references and outcomes each event family may carry. No prompt, chat text, AI response, tool output, raw exception, arbitrary metadata, or caller message is needed.

The existing `AuditLogs` table has a GUID primary key `Id`, nullable `UserId` and `ProjectId`, string `EventType` and `Result`, `CreatedAt`, optional `DeviceId`, generic `EntityType`/`EntityId`, required free-text `Description`, and optional `OldValue`/`NewValue` JSONB. Its row ID could identify a row, but there is no reviewed exact mapping or retry identity for `AuditEventId`. `EventType` and `Result` are generic strings rather than constrained audit enums. `UserId` and `ProjectId` can be null and their foreign keys use SetNull; `ConversationId` is absent. All seven typed optional references are absent. `CreatedAt` is a mutable application value, not an enforced immutable server UTC occurrence time. The table has no event-family constraints. Its required description and generic entity/text/JSON fields cannot be used to pack missing references or sensitive payloads without changing the bounded contract. Therefore no exact sink is feasible on this schema.

## Delivery, ordering, and integrity

The current model has no transactional outbox table, delivery state, delivered/published timestamp, or retry-safe event identity shared with business transitions. The Step 11X observations occur after or around approval, permission, execution reservation/completion, reconciliation, and verification decisions through `AuditObservation`; they are not committed in one database transaction with those changes. A sink failure is observational: it does not change the business decision, roll it back, or retry a handler. That behavior remains unchanged. No atomic business-plus-audit persistence or exactly-once delivery is claimed.

`AuditLogs.Id` is unique as a primary key, but no durable event-ID deduplication protocol exists for retries. `CreatedAt` can support only timestamp sorting; equal timestamps and asynchronous delivery do not establish global, per-action, or per-execution ordering. There is no monotonic event sequence/version. The EF model has no append-only enforcement, prevention of update/delete, hash chain, signature, or immutable database policy. Current audit persistence is neither tamper-evident nor compliance-ready.

A future design needs a separately reviewed typed audit table with required exact scope, typed nullable references, bounded event/outcome and event-family constraints, unique event ID, and immutable server UTC timestamp. To make business changes and audit events atomic, a synchronous insert could share the business database transaction; an asynchronous design needs a transactional outbox with durable event row, unique retry-safe identity, delivery state, created time, optional delivered/published time, and a bounded attempt count only if necessary. Neither design should carry arbitrary payloads. Ordering and append-only/tamper controls require separate explicit guarantees and tests. No outbox, migration, cryptography, or trigger was added here.
