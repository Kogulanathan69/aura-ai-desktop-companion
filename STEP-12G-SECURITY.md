# Step 12G — Permission persistence compatibility and readiness

Step 12G reviewed the existing permission persistence model against the Step 11V `IToolPermissionSource` contract. The schema is insufficient for an exact workflow permission grant, so no persistence adapter was implemented. The default `UnavailableToolPermissionSource` remains the only production implementation, and permission readiness remains false. This is a foundation review, not production permission enforcement.

## Existing model and compatibility

`Aura.Domain.Entities.Permission` maps to the `Permissions` table. It has an `Id` grant identity and required `UserId`; optional `DeviceId` and `ProjectId`; generic text `ResourceType`, `ResourceIdentifier`, `AccessLevel`, and `Status`; optional `GrantedAt` and `RevokedAt`; and creation/update timestamps. Existing project-file features use those generic resource fields for file access. The entity, EF configuration, DbSet, and available repository migration files were inspected; no migration was added.

An exact tool-execution grant must bind a nonempty grant ID to **required, exact** `UserId`, `ConversationId`, `ProjectId`, `ToolId`, and `RequiredPermission`, plus a defined active/revoked state. The current table has no `ConversationId`, `ToolId`, or typed `RequiredPermission` column. `ProjectId` is nullable. `Status` and `RevokedAt` exist, but generic status text is not a dedicated, validated active grant state. Mapping missing dimensions into `ResourceType`, `ResourceIdentifier`, `AccessLevel`, arbitrary text, or JSON would reinterpret project-file permissions and could permit ambiguous or inferred authorization. No role, owner, approval, or tool metadata can create a grant. No wildcard, prefix, contains, project-only, or user-only permission lookup is acceptable.

Because the schema cannot attest all required dimensions, there is no read-only `IToolPermissionSource` database adapter or query. Consequently there is no duplicate-first-match behavior, grant-row fallback, retry, raw SQL, dynamic predicate, or permission database write in this step. The existing `ToolPermissionLookupResult` boundary and `ExactToolPermissionPolicy` remain unchanged. The existing policy rejects inactive and revoked grants, mismatched user/conversation/project/tool/requirement, empty grant IDs, and invalid or wildcard tool identifiers when a future trusted source supplies a grant. Existing checks also show ownership and approval remain separate gates and that tool metadata states only a requirement.

## Runtime boundary and verification

`Aura.Api/Program.cs` does not register a production `IToolPermissionSource` or wire `ToolExecutionPermissionValidator` to one. It still uses `UnavailableRuntimeCapabilityReadiness`, whose permission value is false; informational `PersistenceCapabilityReadiness` also reports permission false. `ProductionAdaptersEnabled` and `ToolExecutionEnabled` default to false, and production-adapter configuration cannot imply permission readiness. Tool execution and Safe File Access remain disabled. No real tool handler or OpenAI/Ollama call was added.

Package-free Step 12G checks inspect EF model metadata and the production source implementations, verify the missing bindings and generic text fields, exercise the unavailable source and cancellation, and assert startup and informational readiness remain false. Existing Step 11V checks cover exact-grant policy, inactive/revoked denials, mismatch denials, and separation from ownership, approval, execution policy, and reservation. Duplicate matching rows must be detected by any future adapter; there is no adapter or database query to test for duplicates in this step. With .NET 10.0.401, `dotnet build Aura.slnx --no-restore` passed and the full offline security suite passed **1,216 checks**. `git diff --check` passed. No live PostgreSQL permission behavior was tested.

Remaining production work requires a separately reviewed schema and migration with explicit required binding columns, constrained active/revoked semantics, and a unique or bounded ambiguity policy; then a read-only exact-match adapter with duplicate detection, cancellation/error handling, offline and live database verification, explicit registration, and a separate production-readiness decision. This step adds no migration, schema, DbSet, EF configuration, package, permission seeding, bypass, or runtime activation.
