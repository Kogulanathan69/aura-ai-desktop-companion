# Step 16F — reconciliation assessment persistence

`ExecutionReconciliationService` previously issued an advisory assessment and returned it without a production writer. This checkpoint adds `IExecutionReconciliationAssessmentWriter` and a concrete `ExecutionReconciliationAssessmentPersistenceWriter`. The writer accepts only immutable assessment evidence, validates exact nonempty action/user/conversation/project/tool/approval/execution IDs, Reserved status/version 1, bounded reason/disposition and UTC time, and inserts one historical row into the existing `ExecutionReconciliationAssessments` table. It never updates execution state, retries, polls, migrates or starts a worker. Multiple assessments intentionally receive distinct generated IDs; there is no single-use or freshness guarantee. A database error produces bounded false; cancellation propagates.

The workflow accepts an optional writer so existing unregistered assessment-only callers retain their behavior. When a writer is supplied, write failure returns fixed `Failed` without evidence or execution-state mutation; success is returned only after the write. The writer is **not registered in normal API startup**, and the production reconciliation source/workflow are likewise unregistered. The Step 14K inspector's `ReviewedReconciliation` catalog remains empty, so **Reconciliation=false**. This change does not claim production persistence readiness.

The schema has `ObservedVersion` and its current constraint permits only Reserved/version 1; no migration is needed for the current historical model. The source read and writer insert are not one transaction with a versioned compare-and-swap: a concurrent completion may make an assessment stale before insertion. Composite foreign keys do not prove every cross-row binding. These gaps, target-bound Step 15B baseline and Step 15F live evidence, a reviewed writer/source DI graph, and repeated-assessment policy must be resolved before production catalog approval. The existing `--live-production-reconciliation-evidence` harness does **not** exercise this new writer; extending and rerunning it on a verified disposable DB is required. No live command ran here.

No runtime flags, reviewed catalogs, production DI, handlers, policy or trusted execution registration changed. All ten composition fields remain false.
