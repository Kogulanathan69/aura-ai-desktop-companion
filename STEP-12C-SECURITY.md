# Step 12C — External authentication subject to internal user mapping

Step 12C adds an unregistered, read-only mapping foundation. ASP.NET bearer authentication keeps `MapInboundClaims = false`; the repository's canonical `sub` is `User.AuthUserId`, not the internal `User.Id` used by `ActionScope` and ownership rows. The two GUIDs are never assumed equal.

`IAuthenticatedUserMappingSource` accepts only an external `AuthUserId` Guid and returns a bounded status plus external and internal GUIDs. Its Application default returns `Unavailable`. `AuthenticatedUserMappingSource` queries existing `Users` with `AsNoTracking`, exact `AuthUserId` equality, and `IsActive`. It projects only `Id`, takes at most two matches, and distinguishes `NotFound`, exactly one nonempty `Found`, and `Ambiguous`. Empty subjects do not query. Duplicate active matches deny even though the existing `UserConfiguration` declares a unique index on nonnullable Guid `AuthUserId`. That configuration is not a substitute for conservative runtime handling. Query errors return `Unavailable`; cancellation propagates. There is no retry, fallback, raw SQL, dynamic query, entity graph, or write.

`HttpCurrentUserContext` reads the current authenticated request on every call. It requires exactly one authenticated identity and one nonempty Guid `sub` belonging to that identity, sends that external subject to the mapping contract, and returns `CurrentUserSnapshot(internal User.Id, Authenticated)` only for `Found` with an exact subject echo and nonempty internal ID. All other statuses, malformed results, mapping failures, missing or duplicate claims, ambiguous identities, and unauthenticated requests return unavailable. The HTTP adapter performs no DB query and exposes no JWT, principal, claims object, role, email, or token to Application. It never falls back to a header, request field, email, username, or alternate claim. Cancellation propagates.

The test-seam composition is: authenticated `sub` → exact active user mapping → internal-ID snapshot → `ExactOwnershipScopeValidator` → `OwnershipPersistenceSource` → exact owned Project conversation and project. It succeeds for a valid distinct external/internal pair and denies foreign conversation/project or scope-user mismatch. Identity still does not prove ownership, permission, approval, or execution eligibility.

`Aura.Api/Program.cs` is unchanged. It still uses `UnavailableRuntimeCapabilityReadiness` and registers neither the mapping source nor `HttpCurrentUserContext`, ownership source, or workflow validator. Runtime ownership readiness remains false; production authorization, tool execution, and Safe File Access remain disabled. `PersistenceCapabilityReadiness` remains informational only. Existing `CurrentUserService` and `UserIdentityService` are unchanged: the older endpoint identity path uses a first matching row and does not apply this new active-user/duplicate check. Harmonizing it would change existing endpoint behavior and is outside Step 12C; it needs separate review before production enablement.

No schema, migration, DbSet, EF configuration, package, JWT claim, permission adapter, audit persistence, handler, or live provider call was added. The package-free tests cover bounded contracts, missing/inactive/duplicate mappings, safe errors, cancellation, fresh request and mapping reads, exact echo, and ownership composition. With .NET 10.0.401, `dotnet build Aura.slnx --no-restore` passed and the full security suite passed 1,138 checks. JWT runtime, EF SQL translation, live PostgreSQL mapping and ownership queries, and production DI integration remain unverified. This is not production authorization readiness.
