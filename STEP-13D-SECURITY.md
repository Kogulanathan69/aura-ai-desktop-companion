# Step 13D: controlled execution-state verification

The package-free security-check executable has a separate `--live-execution-state` entry point. It skips with no connection attempt unless both `AURA_LIVE_EXECUTION_STATE_VERIFY=true` and `AURA_EXECUTION_STATE_DB_IS_DISPOSABLE=true` are set exactly. A valid `ConnectionStrings__DefaultConnection` is then required. Only an explicitly disposable test database is suitable. The ordinary security suite remains offline and exercises the entry point using an injected fake runner.

The live path first verifies connectivity and then reads PostgreSQL catalog metadata and `__EFMigrationsHistory`. It requires the exact `20261014000001_AddActionExecutionStates` migration ID and pre-existing `ActionExecutionStates` table, expected column types and nullability, named checks and Restrict FKs, and unique action, approval, and filtered execution indexes. It does not call `Migrate`, `EnsureCreated`, or other schema mutations. The historical migration baseline/snapshot remains unresolved; presence of this migration ID in a disposable test database is not evidence that the chain is safe for production.

After the schema gate, the harness creates fresh random user, project, conversation, three action IDs, and two approvals using EF. They are internally consistent. It invokes the real unregistered `ActionExecutionStatePersistenceStore` through a context factory. It tests simultaneous initial reservations, one committed Reserved/version 1 row, duplicate reserve, approval reuse, execution ID reuse and rollback of an unreserved Ready insert, stale reservation, wrong action/user/conversation/project/tool/approval/execution ID, cancellation before completion, simultaneous completion, and duplicate completion with unchanged terminal timestamp. Results are checked through fresh EF contexts. No real handler runs.

The harness deletes only rows bearing its generated IDs, in dependent-to-principal order, in `finally`, and verifies their absence. A cleanup failure yields `CLEANUP: FAIL`; there is no broad delete, truncate, database reset, or migration rollback. The output uses fixed PASS/FAIL categories and never emits the connection string, credentials, SQL, exceptions, row values, or IDs.

In this implementation turn the live command was **not run** because a confirmed disposable PostgreSQL database and both explicit gates were not available. Therefore single-winner PostgreSQL concurrency, cleanup against a real schema, and the migration's live behavior remain unverified. Offline checks validate the gate and bounded output, but do not establish live atomicity. The harness does not request serializable isolation, so no serializable isolation claim is made. The individual FKs still do not enforce the complete action/approval/user/conversation/project authorization chain; this is a production blocker requiring separate design and review. Step 13E should run this harness on a reviewed disposable schema, resolve the migration baseline and composite binding integrity, and review production adapter registration only after the wider readiness gates are met.

`Aura.Api` does not register the store or context factory. Startup and informational `ExecutionState` readiness remain false. `ProductionAdaptersEnabled`, `ToolExecutionEnabled`, and Safe File Access remain disabled. There is no production exactly-once claim, real tool execution, or OpenAI/Ollama call.
