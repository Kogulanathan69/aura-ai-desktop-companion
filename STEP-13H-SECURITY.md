# Step 13H — audit outbox dispatcher foundation

This step adds `IAuditOutboxDispatcher` and an unregistered `SecurityAuditOutboxDispatcher`. A caller must supply one nonempty `SecurityAuditOutbox.Id`; the dispatcher never scans or polls the table. There is no hosted service, timer, automatic start, retry loop, production registration, readiness change, or migration. The Step 13G outbox schema is unchanged.

For an exact Pending row, the dispatcher opens a database transaction and issues a conditional EF `ExecuteUpdateAsync` that sets `AttemptCount` to its existing value. PostgreSQL still locks the matching row until the transaction ends. The predicate requires the exact row ID and stable `AuditEventId`, Pending state, zero attempts, and null `DeliveredAt`. A second concurrent caller must wait and then gets a zero-row conflict after the first terminal commit. The row is read again after the lock. The dispatcher checks the exact execution-state binding and reconstructs only ExecutionReserved, ExecutionCompleted, or ExecutionFailed events through `AuditEventRecord.RestoreExecutionOutbox`. That factory validates the existing event ID, event/outcome pair, UTC timestamp, nonempty scope and provenance IDs, and canonical tool ID. It does not generate any new identity or accept arbitrary payloads.

The injected `IAuditEventSink` receives the restored record once. An Accepted result permits Pending → Delivered, `AttemptCount` 0 → 1, and UTC `DeliveredAt`. A bounded failure, unavailable sink, or invalid persisted row permits Pending → Failed with `AttemptCount` 0 → 1 and null `DeliveredAt`. The terminal transition is another conditional EF update in the same transaction. Delivered and Failed cannot be dispatched again. Any zero-row update fails closed as Conflict. Cancellation propagates; an interrupted transaction rolls back and may leave Pending with zero committed attempts. This reflects the Step 13G check constraint. A database failure returns a bounded Unavailable result. No handler, file, AI provider, or external payload is involved.

The existing database check permits a manually written Failed row with a nonnull `DeliveredAt`; the dispatcher never writes that shape. Database-wide enforcement of the Failed timestamp invariant would require a reviewed follow-up migration, so this foundation claims the invariant only for its own transition path.

The existing `SecurityAuditPersistenceSink` now treats a duplicate `SecurityAuditEvents.Id` as Accepted **only when every stored typed field matches the requested event**, comparing its UTC timestamp at PostgreSQL microsecond precision. A mismatched duplicate remains Failed. This makes an explicit later attempt with the same stable event ID safe for the database sink if its insert committed before the outbox transaction committed. The dispatcher does not itself retry. An arbitrary injected sink can have side effects outside the database, and a crash or cancellation after such a side effect can leave the outbox Pending. Exactly-once delivery and duplicate-free external side effects are **not** claimed. A transaction held across sink delivery also requires the sink to use a separate available database connection; this has not been tested with PostgreSQL on this PC.

Offline checks cover the bounded restore factory, exact identity/scope preservation, rejected malformed events, invalid/cancelled dispatcher calls, conditional Pending and terminal update structure, stable audit identity, duplicate-safe database sink mapping, and disabled runtime configuration. They cannot prove PostgreSQL row-lock behavior, crash recovery, or transaction timing. No live database verification or migration application was performed. Production AuditSink and ExecutionState readiness remain false; production adapters, tool execution, and Safe File Access remain disabled.

Step 13I should review this transaction/connection strategy against a disposable PostgreSQL database, test two concurrent dispatchers and crash windows, verify the exact duplicate path and terminal constraints, and decide whether a durable in-progress claim, manual recovery policy, or external-delivery idempotency protocol is needed before production registration.
