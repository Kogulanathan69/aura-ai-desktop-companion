## Proof semantics and authoritative source

The only candidate is `owned-project-metadata-read`. `OwnedProjectMetadataExecutionEvidenceSource` receives the workflow's exact action ID, server scope and execution ID. Under a repeatable-read transaction it reads one terminal durable `ActionExecutionStates` row with exact action/user/conversation/project/tool/approval/execution bindings, consumed approval, and version 2. It checks the active user, project conversation, action and approval chain, then independently queries `Projects` for the exact project ID and owner. The observation contains only `ProjectId`, persisted `UpdatedAt`, `ProofSource=OwnedProjectMetadata`, and `ProofVersion=1`. There is no name, path, description, URL, content, arbitrary metadata or handler result. A failed execution has a Failed report and no project observation. Missing or malformed authoritative state returns no evidence; cancellation propagates and other database errors are suppressed.

The observation means that the approved project target existed and was owned when queried. A project metadata read is non-mutating; this does not prove that a future handler returned an exact serialized response, and no handler is available yet. Any stronger result-content claim needs a separately reviewed binding and proof model. The workflow now passes the action ID to the source and denies a `Verified` outcome unless the successful report has exact execution version 2, candidate tool ID, same-project observation, UTC persisted timestamp and exact source/version pair. The conservative policy still returns Failed for a failed report and Inconclusive otherwise. Handler success alone remains Inconclusive. Wrong action, user, conversation, project, tool, approval, execution ID, version or proof pair cannot be promoted by this workflow.
