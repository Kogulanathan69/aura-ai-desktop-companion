# Step 12B — Authenticated current-user boundary foundation

The API already authenticates JWTs with ASP.NET bearer middleware, sets `MapInboundClaims = false`, and reads the canonical `sub` claim in `CurrentUserService`. That subject is stored as `User.AuthUserId`. Existing `UserIdentityService` then looks up the distinct internal `User.Id`, which is the ID used by `ActionScope`, conversations, projects, and `OwnershipPersistenceSource`. There is no repository-issued internal-user-ID claim. This identity mapping cannot be inferred from the subject GUID.

`HttpCurrentUserContext` is a deliberately unregistered host adapter for `ICurrentUserContext`. It reads the current authenticated `ClaimsPrincipal` from `IHttpContextAccessor` afresh on each call. It recognizes only one nonempty Guid `sub`; absent context, unauthenticated identity, absent/duplicate/malformed/empty subject, and exceptions return an unavailable `CurrentUserSnapshot`. Cancellation propagates. Headers, routes, request bodies, alternate claim names, email, and roles are not consulted. No JWT is parsed manually, and no principal, token, raw claim, role, or email is returned to Application.

Even a valid `sub` returns unavailable: it identifies `AuthUserId`, not the internal `User.Id` required by the contract. The adapter performs no database lookup, as required for this step. A later reviewed design must resolve that mapping without confusing external and internal IDs before this context can be registered. Existing `CurrentUserService` and `UserIdentityService` behavior is unchanged.

The package-free composition check combines `HttpCurrentUserContext`, `OwnershipPersistenceSource`, and `ExactOwnershipScopeValidator` against matching in-process ownership rows. It denies before querying the database because internal identity is unavailable. Passing a scope with either the internal ID or external subject cannot manufacture authenticated ownership. Step 12A's separate ownership checks remain in force; neither identity nor ownership implies permission, approval, or execution. No role authorization or fallback was added.

`Aura.Api/Program.cs` still registers `IHttpContextAccessor` for existing services but does not register `HttpCurrentUserContext`, `OwnershipPersistenceSource`, or `ExactOwnershipScopeValidator` for production workflows. It still constructs `UnavailableRuntimeCapabilityReadiness`; ownership readiness remains false at startup. Runtime safety defaults and Safe File Access remain disabled. No production authorization, tool execution, persistence write, schema/migration/EF/package change, or live OpenAI/Ollama call was added.

The tests cover canonical-sub ambiguity, invalid principals and claims, fresh context reads, bounded results, no DB dependency in the adapter, denied composition, and cancellation. With .NET 10.0.401, `dotnet build Aura.slnx --no-restore` passed and the full suite passed 1,107 checks. JWT verification, external-to-internal ID mapping, EF SQL translation, and live PostgreSQL ownership remain unverified. This foundation is not production authorization readiness.
