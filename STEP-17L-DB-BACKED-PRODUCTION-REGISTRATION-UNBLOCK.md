# Step 17L — DB-backed production registration unblock review

## Purpose and evidence boundary

This review revisits ExecutionState, Reconciliation, AuditSink, AuditDelivery, Ownership and Permission after the Step 17K operator-reported same-target PASS. Step 17K closes the verifier's bounded current catalog and five targeted migration-history checks for the operator-attested disposable target (`aura_disposable_test`, OID `24576`, system identifier `7696813047573034172`). Earlier Step 17A/17F records lack matching target identifiers, so continuity is operator-attested rather than independently cross-matched. Historical core-schema provenance is **partially unresolved**: no checked-in core-creation migration, model snapshot or reviewed external baseline deployment record ties the initial core tables to this target. Current catalog shape cannot establish that history.

**Decision: no DB-backed production capability is objectively ready for catalog approval in this checkpoint. No production registrations or catalog entries were added.** The bounded schema blocker is closed, but the independent requirements below are not. In particular, the Step 17K result cannot substitute for a registration graph, cross-entity integrity, a real JWT, revoked-grant denial, or a recovery policy. This is a review of normal-startup composition; it does not run a live harness, apply migrations, enable execution or create a worker.

## One DbContext/factory architecture

Normal `Aura.Api/Program.cs` has exactly one `AddDbContext<AuraDbContext>` configured with Npgsql and pgvector plus one scoped `IAuraDbContext` alias to that same scoped context. Ownership and Permission sources consume the alias. ExecutionState, Reconciliation source/writer, AuditSink and AuditDelivery require `IDbContextFactory<AuraDbContext>`, which normal startup does not provide. There is no singleton capturing a scoped context today. Adding a factory alongside the existing `AddDbContext` without review could duplicate context/options descriptors or create incompatible option lifetimes.

When a factory-backed capability clears its independent blockers, replace the existing registration in one change with a single `AddDbContextFactory<AuraDbContext>` configured once with the current `UseNpgsql(...UseVector())` options. Keep the existing scoped `IAuraDbContext` alias to the factory-provided scoped `AuraDbContext`; verify one context descriptor, one factory descriptor, compatible options, and scope resolution with `ValidateScopes` and `ValidateOnBuild`. Use a singleton factory and scoped application adapters. Do not add a pooled factory, a parallel `AddDbContext`, startup connection access, `Migrate`, `EnsureCreated`, or migration execution. This is a reviewed design, **not** an implemented DI change; adding unused factory machinery now would not make any capability ready.

## Capability decisions

| Capability | Step 17K effect | Registration and remaining blocker |
| --- | --- | --- |
| ExecutionState | Bounded current state table, constraints and targeted history PASS | **false.** `ActionExecutionStatePersistenceStore` is unregistered and has no factory. Before its initial row insert, it validates the supplied binding's shape but does not query the active user, owned project/conversation, matching `AIActions` row, or an approved, unexpired `ActionApprovals` row belonging to that action and user. Separate foreign keys permit a cross-entity mismatch. The smallest safe correction is a fail-closed, same-transaction pre-insert chain/lifecycle query, followed by a new controlled live run that exercises mismatched and invalid approval rows. Exact approval-state policy must be reviewed before choosing predicates. `CommitAsync` failure may mean committed or rolled back; callers must treat `Unavailable` as unknown and read back by action/execution ID before any new effect. Exactly-once external effects are **not** an ExecutionState readiness requirement. Factory graph and exact catalog still need review. |
| Reconciliation | Bounded assessment schema and targeted history PASS | **false.** The source reads an internally consistent snapshot in a RepeatableRead transaction; the writer inserts later through another context. The contract and current consumers treat assessments as **point-in-time historical advisory** records: `SafeToMarkFailed` does not mutate durable state or authorize a current transition. A completion between source read and insert makes the record stale as a *current decision* but does not falsify its recorded observed version/time. Every future decision consumer must re-read durable state; no freshness guarantee is claimed. The remaining blocker is the full reviewed scoped source/writer/service/validator/policy graph: `IExecutionReconciliationAssessmentWriter` is optional in the service constructor, while the current inspector checks only the source descriptor. A source-only catalog entry would falsely signal the complete writer path. Make the writer mandatory in the production composition rule and verify the exact graph before approval. |
| AuditSink | Bounded audit-event schema and targeted history PASS | **false.** The direct `SecurityAuditPersistenceSink` has bounded statuses, exact duplicate-ID matching and cancellation propagation, and the Step 15E review records the live persistence/recovery evidence path. Its separate transaction can fail after a business state commit; retention, append-only/tamper and operational failure policy remain unapproved. It lacks a normal-startup factory, scoped registration and catalog entry. A direct sink is not a substitute for a transactionally staged outbox intent. |
| AuditDelivery | Bounded outbox schema, latest hardening ID and targeted history PASS | **false.** The explicit one-item dispatcher has no worker, polling or automatic retry. It calls the database sink under an outbox row lock, but the sink commit and `Delivered` state commit are separate. A crash or ambiguous failure after the sink commit can leave `Pending`; a later explicit replay is safe only for an exact matching event ID and the reviewed database sink. Step 14J does not require true external exactly-once delivery, but it does require an explicit recovery/idempotency decision. No general external sink or automatic retry can be inferred from the current database duplicate check. Define how unknown outcomes are reconciled against the audit event and outbox row before permitting a later explicit dispatch; review the scoped dispatcher/sink/factory graph and catalog. |
| Ownership DB side | Selected Users/Projects/Conversations shape and constraints PASS | **false.** The authenticated raw JWT `sub` must map through `Users.AuthUserId` to active local `Users.Id`; project and conversation lookups require that local ID. Step 15A does not prove a real signed Supabase JWT or denial against a pre-existing foreign-owned row. The intended scoped context/mapping/source/validator graph also has an alias-versus-exact-descriptor mismatch with the inspector. Do not assert ownership readiness from schema or a synthetic identity. |
| Permission DB side | Selected grant shape, keys and constraints PASS | **false.** `ToolPermissionPersistenceSource` filters exact active grants and `RevokedAt == null`, but the reviewed Step 15C run reported `REVOKED GRANT CHECK: NOT PROVEN`. A real separate revoked fixture and its denial must pass on the verified target before exact registration/catalog review. Do not treat absence of a grant as revoked-grant evidence. |

The original core-schema creation provenance remains a separate unresolved review item for all DB-backed paths.
